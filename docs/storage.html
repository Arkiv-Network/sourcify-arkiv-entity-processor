Different hashes answer different questions

Content hashes find shared bodies. Staging IDs identify complete semantic entities. Payload checksums protect bytes in transit. They should not be used interchangeably. Arkiv code.hash is Keccak-256 of raw bytecode. Do not substitute upstream relational IDs or code indexes for this content reference.

Compilation hash is not the dedup authority

A full canonical compilation-payload hash and the processor’s indexed fingerprint are different definitions. The processor retains its existing fingerprint; it does not claim compatibility with a full-payload hash. Its semantic staging ID includes the represented payload and attributes (a spill stub includes the complete-body hash), so payload differences still distinguish entities.

Two consequences of the current fingerprint

  • Same index, different entities: a metadata-only change can leave the indexed compilation hash unchanged. The payload changes, so the semantic staging ID still distinguishes the entities.
  • Same payload, extra entities: the fingerprint includes onchain bytecode hashes, although the compilation payload stores the recompiled hashes. A change only to onchain bytecode can therefore produce different compilation attributes and staging IDs for identical compilation payloads. This can create redundant compilation entities; its prevalence has not been measured.

Compression and oversized payloads

The verified_contract logical payload is the complete input JSON, with no injected schema marker. Decode compression and resolve any spill parts before comparing it with the input. Full records are larger than the previous selected-field payloads and may need more blob parts; regenerate old bundles.

  1. Build the logical entity payload. Bodies over 122,880 bytes become a small $spill stub plus 100,000-byte blob slices.
  2. Apply gzip level 6 to each entity payload only when it reduces its size; otherwise use identity. The processor enforces a 120,000-byte wire-payload limit. Preserve original content type and payload checksum.

Interpreting a stored payload

A consumer needs to reverse these storage layers:

  1. Decode transport compression and validate the entity checksum.
  2. If spilled, gather every part, validate indexes, counts and byte lengths, then verify the complete SHA-256.
  3. Validate source SHA-256 or bytecode Keccak content references before interpreting the contract data.

Gzip is intentional. It changes stored bytes, not the decoded contract data. A consumer should reject missing or corrupt dependencies. These are decoding requirements, not an HTTP reader implemented by this processor.
