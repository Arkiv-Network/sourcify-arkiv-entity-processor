How stripped JSON becomes the full record

The v3 storage format separates reusable values from deployment-specific data. Gzip decoding alone shows a stripped envelope, not the original Sourcify response. Hydration is the final step.

verified_contract: {schema, data, references}
    ├─ compilation hash → compilation: {schema, data, references}
    │      ├─ source SHA-256 → sourcefile content
    │      ├─ bytecode Keccak-256 → code bytes
    │      └─ local pointer → an equal value in this compilation
    └─ bytecode Keccak-256 → onchain code bytes
                  ↓ hydrate
       complete original contract JSON

Reference manifest

Each envelope contains data and a separate references array. A reference’s path is the destination JSON Pointer: ~1 escapes a slash and ~0 escapes a tilde. Referenced object keys are absent from stored data; referenced array positions retain null placeholders so indexes stay stable. The manifest distinguishes these placeholders from original null values and restores the referenced content during hydration. Literal user objects named $ref remain ordinary input data.

  • kind: sourcefile resolves exact source text by SHA-256.
  • kind: code resolves bytes by Keccak-256; encoding preserves the original hex prefix and uppercase positions.
  • kind: compilation selects a field from the hydrated shared compilation using pointer.
  • kind: local restores an equal standard-JSON subtree when the reference is smaller than repeating it from another pointer in the same compilation. External dependencies resolve first.

Use the actual generated example to follow references and compare stored and hydrated JSON. These are content references, not Sourcify database IDs or Arkiv entity keys. The typed compilationref attribute additionally links the verification to its compilation entity key.

Different hashes answer different questions

Here canonical JSON means sorted object keys with exact number representations preserved. It is not a claim of complete RFC 8785 normalization. Arrays retain their order.

Compression, spill and hydration

  1. Read the seed entity and decode gzip or identity. Check its payload checksum.
  2. For a spill stub, collect all blob parts in order and validate count, lengths and the complete SHA-256.
  3. Resolve the v3 reference manifest, validate target content hashes, and restore values at their exact JSON Pointer paths.
  4. Return the hydrated original JSON, without storage schema, data or references wrappers.

Logical bodies over 122,880 bytes spill into 100,000-byte slices. Gzip level 6 is applied only when smaller; the wire payload limit is 120,000 bytes. These transport layers remain separate from semantic references.

arkiv-entity-processor hydrate BUNDLE_DIR > hydrated.ndjson

The reader uses seed entity files and works with an extracted prefill archive. Missing or corrupt dependencies cause failure. A failed stream must not be treated as a complete dataset. This CLI is an offline reader; the repository does not provide an HTTP API server.

Migration and size claims

Version 3 changes verification and compilation schemas, hashes and keys. Regenerate old bundles and update consumers; never interpret stripped data as the original record. Existing deployed readers have not been upgraded by this processor change. The example reports decoded payload bytes, compressed wire payload bytes and JSONL framing separately. Sharing can remove repeated bodies, but one contract cannot establish whole-dataset savings.
