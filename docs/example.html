Follow one contract into its entities

A verification record says which contract was checked. Its linked entities hold the compilation, source text and bytecode.

Synthetic example, with shortened payloads and symbolic hashes. It explains storage relationships; it is not a real verification result or a runnable input record.

1. Information in the source record

{
  "chainId": "1",
  "address": "0x0000000000000000000000000000000000000001",
  "matchId": "42",
  "match": "exact_match",
  "runtimeMatch": "exact_match",
  "creationMatch": null,
  "abi": [],
  "sources": {"Counter.sol": {"content": "contract Counter {}"}},
  "metadata": null
}

The source says the runtime bytecode matches exactly. It reports no creation match and no metadata. An empty ABI is a known empty list, which differs from an unknown ABI (null).

The verified-contract entity also has a typed compilationref attribute pointing to the compilation’s Arkiv key. A content hash such as H_source is a different kind of reference: it identifies shared content, not an Arkiv entity key.

3. Compare values, not just entity counts

  • The source text and its file path must still agree.
  • Match status and original identifiers must survive unchanged.
  • metadata: null must stay null; it is not an empty object.
  • Each non-null bytecode reference must identify the expected bytes.

These are comparison criteria, not claims of a completed full-dataset audit. Oversized payloads add blob entities without changing the logical information.
