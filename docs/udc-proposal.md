# Proposal: the Sourcify dataset on UDC entities

Status: proposal, 2026-10-28, on branch `udc`. The open questions but Jalebi's were decided on 2026-10-28
([decisions](#decisions-of-2026-10-28)), and steps 3 and 5 of the [plan](#ordered-plan) are implemented on this
branch and tested on our node: v4 bundles, their readers, the UDC sync with contracts patched in place, and the
server's v4 backend. The daily v4 seed (`SEED_FORMAT=udc`, its own R2 prefix and pointer, the mirror's sync
paused for `prepare` only) is wired and stub-tested; it has not run. Nothing here is merged or deployed. `main`, `develop` and `master` of the Sourcify
repositories stay untouched until after 10 November 2026; every step that needs a default branch waits until then
([migration](#migration)). The UI (step 6) reads the test dataset on our node through the
[reader contract](#reader-contract-for-the-ui).

Arkiv entities moved to the user-defined-columns (UDC) model: no payload and no content type, only typed
attributes (`bool`, `i32`, `u64`, `u256`, `dec`, `bytes32`, `bytes`, `str`, `addr`, `key`), each indexed or
stored only, `bytes` never indexed, and the schema named by the indexed `str` attribute `arkiv.schema`. The v3
dataset ([SCHEMA.md](https://github.com/Arkiv-Network/sourcify-arkiv/blob/develop/docs/SCHEMA.md)) was built
around one gzip payload per entity, JSON envelopes with a `references` array, spill blobs and five transport
attributes. This proposal replaces that storage layer with a UDC one, **v4**. It keeps the logical
decomposition the processor already performs (`src/split.rs`): every value, and the hydrated key order,
stay what v3 hydration produces today.

## Decisions in brief

- **Five kinds, one schema generation.** `sourcify.v4.contract`, `sourcify.v4.compilation`, `sourcify.v4.source`,
  `sourcify.v4.code` and `sourcify.v4.chunk`, named by `arkiv.schema`. The tag replaces `projectid`, `kind` and
  `uploadschema`; the generation prefix (`sourcify.v4.`) lets one `STARTSWITH` scope a whole dataset (decided).
- **Content in bytes attributes, not payloads.** Each bytes value starts with a codec byte: identity, raw
  DEFLATE, or a chunk list. Digests are over uncompressed bytes, so compression never changes identity. No zstd
  (decided; codec `03` stays free).
- **A 120,000-byte budget per entity.** Below the node's 128 KiB so that a create also fits a reth transaction
  (a reth pool refuses transactions over 131,072 bytes by default). Values over budget move into `chunk` entities.
  Compressing before the budget check turns v3's 196,824 spill blobs into **963 chunks**.
- **Compilation split for the hot read.** `abi` and `compilation` are attributes of their own, so
  `fields=abi,compilation` (154 of 190.8 million single-contract lookups in Sourcify's seven-day query profile)
  reads about 1.75 KB of one entity; every
  other compiler-owned field shares one `artifacts` attribute (per-field attributes would cost 15% more bytes,
  measured). No separate `digests` attribute (decided, [below](#decisions-of-2026-10-28)): the hot read keeps
  reading the `manifest`.
- **Cross-entity references are `key` attributes.** The contract names its compilation and on-chain code
  (`compilationref`, `creationcoderef`, `runtimecoderef`, with the compilation's hash in the indexed
  `compilationhash`); the compilation names its recompiled code
  (`creationcoderef`, `runtimecoderef`) and lists its sources' keys in `sourcerefs`, because a compilation can
  have up to 390 sources and an entity at most 32 attributes. No `references` array crosses entities any more.
- **Keys are the node's.** A key is `keccak256(chainId ‖ 0x4400…0044 ‖ owner ‖ entity nonce ‖ salt)` on both
  nodes. Writes use salt 0, so a prefill's keys are a pure function of its order; deduplication is by content
  hash (indexed `hash`), as today.
- **Everything permanent, one owner per chain.** `expiresAt = 2^64 − 1` for every entity; on each chain one dataset
  key owns and creates all of it (decided: a key per chain, [below](#decisions-of-2026-10-28)). Under the one-year
  rent cap, permanence costs one year of rent.
- **Contracts are patched in place** (decided). A re-verification under a new `matchId`, or a correction under the
  same one, patches the address's contract entity: every attribute is set again, attributes the new version lacks
  are unset, and the key stays. Sources, codes, compilations and chunks are never changed or deleted; a new version
  that needs another compilation gets a new compilation entity first. Measured on both nodes, a patched entity keeps
  its creation position in results and only its `updatedAt` moves.
- **Queries both nodes run.** No `NOT`/`!=` (Jalebi refuses both), no `BETWEEN` (both refuse it), at most
  eight `OR` groups (our node's planned path), `limit` at most 100. **Paging by `matchid` windows**: a window
  query that returns fewer than `limit` rows, or no cursor, holds every match in it, whatever order the node
  returns ([paging](#paging)); node order and cursors are never relied on across queries.
- **The indexed set and the stored signatures stay as proposed** (decided: price does not matter for a prefill and
  for Sourcify): 19 indexed contract attributes (21 with the proxy pair), `chainid`, `isproxy`/`proxytype` and
  `evmversion` included; `signatures` stored in `artifacts`.
- **Lossless, byte for byte.** v4 hydration equals v3 hydration: the SafeProxy example rebuilds
  `docs/data/hydrated-contract.json` exactly, 100,000 real records come back byte-identical through
  `process --format udc` and `hydrate`, and the 16 contracts the UDC sync wrote to our node read back and serve
  byte-identically to the v3 path ([evidence](#prototype-and-evidence)).

## Entity kinds

The full corpus is the processor's daily seed of 2026-10-23, which our node's previous (payload-era) chain was
prefilled from: 7,901,941 contracts, 15,327,933 entities, 38.09 GB of gzip payloads. All counts below are
measured on it (`udc/measure/results/corpus-20261023.json`, `v4size-20261023.json`).

| v3 kind | Count | v4 kind | Decision |
| --- | ---: | --- | --- |
| `verified_contract` | 7,901,941 | `contract` | **Keep.** One per address: the root a reader finds by address, carrying every query attribute. |
| `compilation` | 878,407 | `compilation` | **Keep**, shared by content hash (9 contracts per compilation on average). Fields regrouped into `abi`, `compilation`, `artifacts`. |
| `sourcefile` | 1,135,778 | `source` | **Keep**, shared by SHA-256 of the text: 5,836,160 source references point at 1,135,778 sources. |
| `code` | 5,214,983 | `code` | **Keep**, shared by Keccak-256. |
| `blob` | 196,824 | `chunk` | **Replace.** Only a value whose *compressed* size exceeds the budget is chunked: 963 chunks for 543 values. |

Alternatives considered and rejected:

- **On-chain bytecode inside the contract.** It would save one entity per contract and one read, but bytecode is
  heavily shared: 7,901,941 runtime references point at 986,545 distinct codes (the most common one is shared by
  1,595,579 contracts) and 7,741,722 creation references at 2,973,236. Inline, the contracts would hold 42.6 GB of
  raw bytecode instead of 22.0 GB of distinct code.
- **Sources inside the compilation.** 5.8 million source references for 1.1 million sources; the sharing would be
  lost.
- **One entity per compilation field** (an `abi` entity, a `metadata` entity, …). UDC already lets a reader
  select single attributes, so separate entities would only add 1,460 storage units each and more reads.
- **Field-level sharing of large fields.** After v3's local references, `stdJsonInput` is a stub (2,075 distinct
  values, 0.04 GB in total); `stdJsonOutput` is unique per compilation (877,644 distinct of 878,392) and `metadata`
  too (875,734 distinct). Only `abi` repeats (377,751 distinct, 0.57 GB in total): sharing it would save about
  0.3 GB but add an entity and a read to the hot `abi,compilation` path.
- **Merging contract and compilation.** A compilation is shared by 9 contracts on average.

## Bytes values: encoding, budget and chunks

Every `bytes` attribute except a chunk's `data` is one *codec byte* followed by a body:

| Codec | Body |
| --- | --- |
| `00` identity | The value itself (UTF-8 JSON, source text, raw bytecode or a key list) |
| `01` raw DEFLATE | RFC 1951 stream of the value, used when it is shorter than identity |
| `02` chunk list | `sha256(joined) ‖ u32 length(joined) ‖ key₀ ‖ key₁ ‖ …`: the encoded value (codec byte included) split into chunks of at most 120,000 bytes |

- **Why a codec byte** rather than gzip detection (v3's `contentencoding`) or an encoding attribute: a value can
  start with `1f 8b` by chance, and an attribute per value would spend the 32-attribute budget.
- **Why raw DEFLATE** rather than gzip, zstd or brotli: every client has it (Rust `flate2`, Python `zlib`, Node
  `zlib`, browsers' `DecompressionStream("deflate-raw")`), it has no 18-byte gzip frame per value, and integrity
  comes from SHA-256 digests anyway. zstd with a trained dictionary would compress small JSON better but has no
  browser decoder; it can be added later as codec `03` ([open questions](#open-questions)).
- **Why compress per attribute.** Selectable attributes are the point of UDC. Measured over all 878,392
  compilations (`udc/measure/results/groups-20261023.txt`): one compressed document per compilation is the
  smallest (11.92 GB); one attribute per field costs **+15.3%** (13.74 GB); `abi` + `compilation` together and the
  rest in one attribute **+4.9%** (12.50 GB); v4's three groups `abi`, `compilation`, `artifacts` **+5.1%**
  (12.52 GB).
- **Budget.** The `bytes` values of one entity total at most **120,000 bytes**. The node allows 131,072, but a
  131,072-byte create is a 131,768-byte signed transaction, over a reth pool's 131,072. 120,000 bytes plus 24
  attributes is a 125,112-byte transaction (measured). It is also the v3 writer's limit.
- **Chunking.** While an entity is over budget, its largest value (the `manifest` only when nothing else is left,
  `sourcerefs` never) moves into `chunk` entities, created first, and the attribute keeps a chunk list. A
  reader joins the chunks, checks length and SHA-256, then decodes. In the corpus 339 compilation `artifacts`
  values and 204 source texts are chunked: 963 chunk entities. Everything else, including 79,512 of v3's 80,081
  spilled payloads, fits once compressed.

## Attributes per kind

Indexed attributes are what queries can reach; stored-only ones are returned but never matched. Every name
and type below is what `src/udc.rs` writes and what our node returned (`docs/udc-examples/safeproxy-node/readback.json`).
The SDK's view of the same thing:

```ts
import { addr, bool, bytes, bytes32, defineSchema, i32, key, str, u64 } from "@arkiv-network/sdk/schema"

const Contract = defineSchema("sourcify.v4.contract", {
  address: addr().indexed(), chainid: u64().indexed(), matchid: u64().indexed(), verifiedat: u64().indexed(),
  match: str().indexed(), name: str().indexed(), compilerversion: str().indexed(), language: str().indexed(),
  evmversion: str().indexed(), optimizer: bool().indexed(), optimizerruns: i32().indexed(), viair: bool().indexed(),
  deployer: addr().indexed(), blocknumber: u64().indexed(), abihash: bytes32().indexed(),
  creationcodehash: bytes32().indexed().optional(), runtimecodehash: bytes32().indexed().optional(),
  compilationhash: bytes32().indexed(), compilationref: key(),
  creationcoderef: key().optional(), runtimecoderef: key().optional(),
  isproxy: bool().indexed().optional(), proxytype: str().indexed().optional(),
  data: bytes(),
})
const Compilation = defineSchema("sourcify.v4.compilation", {
  hash: bytes32().indexed(), manifest: bytes(), abi: bytes(), compilation: bytes(), artifacts: bytes().optional(),
  sourcerefs: bytes().optional(), creationcoderef: key().optional(), runtimecoderef: key().optional(),
})
const Source = defineSchema("sourcify.v4.source", { hash: bytes32().indexed(), content: bytes() })
const Code = defineSchema("sourcify.v4.code", { hash: bytes32().indexed(), code: bytes() })
const Chunk = defineSchema("sourcify.v4.chunk", { data: bytes() })
```

### `sourcify.v4.contract`

| Attribute | Type | Indexed | Value |
| --- | --- | --- | --- |
| `arkiv.schema` | `str` | yes | `sourcify.v4.contract` |
| `address` | `addr` | yes | The contract address |
| `chainid` | `u64` | yes | Source chain, `1` |
| `matchid` | `u64` | yes | Sourcify `matchId` |
| `verifiedat` | `u64` | yes | `verifiedAt` in Unix seconds |
| `match` | `str` | yes | `match`, or the text `null` |
| `name` | `str` | yes | `compilation.name` (at most 128 bytes, v3's truncation) |
| `compilerversion`, `language`, `evmversion` | `str` | yes | As in v3 (defaults `unknown`, `unknown`, `default`) |
| `optimizer`, `viair` | `bool` | yes | As in v3 |
| `optimizerruns` | `i32` | yes | **New on the contract** (v3 had it on the compilation only) |
| `deployer` | `addr` | yes | `deployment.deployer`, zero address if missing |
| `blocknumber` | `u64` | yes | `deployment.blockNumber`, 0 if null |
| `abihash` | `bytes32` | yes | SHA-256 of the canonical ABI JSON; equals the compilation's `abi` digest |
| `creationcodehash`, `runtimecodehash` | `bytes32` | yes, when the code is not empty | Keccak-256 of the on-chain bytecode |
| `compilationhash` | `bytes32` | yes | The compilation's `hash` (Search's "same compilation"; the reader checks it) |
| `compilationref` | `key` | no | The compilation entity |
| `creationcoderef`, `runtimecoderef` | `key` | no | The on-chain bytecode's `code` entities |
| `isproxy`, `proxytype` | `bool`, `str` | yes, when supplied | As in v3 (no corpus entity has them) |
| `data` | `bytes` | no | The contract-local JSON: v3's stripped `data`, without the on-chain bytecode the two code references restore, in v3's key order |

22 to 25 attributes (the SafeProxy example has 25, 21 indexed). Hashes are indexed, keys are not: a content hash
means the same thing for any owner and chain and is what questions ask about, a key is only for fetching. An
on-chain bytecode is referenced only when it is spelled `0x` + lowercase hex and no other contract-local reference
follows it in its lane (the only case in the corpus); otherwise it stays literal in `data`, where v3's reference
order put it. Indexed strings are projections: control characters (which a `str` may not hold) become U+FFFD, and
more than 128 bytes become a 125-byte prefix and an ellipsis, as in v3.

### `sourcify.v4.compilation`

| Attribute | Type | Indexed | Value |
| --- | --- | --- | --- |
| `arkiv.schema` | `str` | yes | `sourcify.v4.compilation` |
| `hash` | `bytes32` | yes | SHA-256 of the `manifest` bytes: the compilation's identity |
| `manifest` | `bytes` | no | Canonical JSON `{codes, digests, refs, sources}` (below) |
| `abi` | `bytes` | no | The `abi` field (canonical JSON) |
| `compilation` | `bytes` | no | The `compilation` field |
| `artifacts` | `bytes` | no | Every other compiler-owned field, one canonical JSON object: `additionalInput`, `sources`, `signatures`, `metadata`, `storageLayout`, `transientStorageLayout`, `userdoc`, `devdoc`, `sourceIds`, `stdJsonInput`, `stdJsonOutput` and the two lanes' `recompiledBytecode`, `sourceMap`, `linkReferences`, `immutableReferences`, `cborAuxdata` (under `creationBytecode`/`runtimeBytecode`), as v3 stripped them |
| `sourcerefs` | `bytes` | no | Codec `00` and the 32-byte keys of the sources, in `manifest.sources` order. Never chunked: its keys must stay where re-keying can rewrite them (a chunk list's digest would bind them), so a compilation holds at most 3,749 sources (the corpus's largest has 390); readers refuse any other codec |
| `creationcoderef`, `runtimecoderef` | `key` | no | The recompiled bytecode's `code` entities (two slots: a lane's recompiled bytecode takes its lane's slot, any other code a reference names takes the free one) |

The manifest holds what v3 kept in the envelope's `references`, with cross-entity targets named indirectly:

```json
{
  "codes": {"creation": "0x<keccak>", "runtime": "0x<keccak>"},
  "digests": {"abi": "0x<sha256>", "artifacts": "0x<sha256>", "compilation": "0x<sha256>"},
  "refs": [
    {"kind": "local", "path": "/stdJsonInput/settings", "pointer": "/compilation/compilerSettings"},
    {"kind": "source", "path": "/sources/contracts~1proxies~1SafeProxy.sol/content", "source": 0},
    {"kind": "code", "path": "/creationBytecode/recompiledBytecode", "code": "creation",
     "encoding": {"prefix": true, "uppercase": []}}
  ],
  "sources": ["0x<sha256 of the source text>"]
}
```

`digests` are SHA-256 of each group's stored (uncompressed) JSON; `sources` are the sources' content hashes,
aligned with `sourcerefs`; `codes` are the recompiled bytecodes' Keccak-256, behind the `creationcoderef` and
`runtimecoderef` keys. Because the manifest commits to all content but to no key, `hash` is the same for the
same compiler output on any chain and for any owner, and the writer deduplicates on it. Contract and
compilation attribute names stay lowercase, as in v3, so existing queries keep their names.

Compiler attributes (`compiler`, `compilerversion`, `language`, `name`, `evmversion`, `optimizer`,
`optimizerruns`, `viair`) are no longer indexed on the compilation: every question returns contracts, and the
contract carries them. Each indexed attribute costs 128 storage units per entity; a patch can index an attribute
later if a question needs compilations.

### `sourcify.v4.source`, `sourcify.v4.code`, `sourcify.v4.chunk`

| Kind | Attribute | Type | Indexed | Value |
| --- | --- | --- | --- | --- |
| source | `hash` | `bytes32` | yes | SHA-256 of the UTF-8 text (as v3) |
| source | `content` | `bytes` | no | The text itself, no JSON wrapper (v3's `{"content","schema"}` wrapper was 0.83 GB before compression) |
| code | `hash` | `bytes32` | yes | Keccak-256 of the bytecode (as v3) |
| code | `code` | `bytes` | no | Raw bytecode |
| chunk | `data` | `bytes` | no | One slice of an encoded value, no codec byte |

## Hydration

### Algorithm

`Reader::hydrate` in `src/udc.rs`. For a contract entity `C`:

1. Check `C`: owner is the dataset owner, `arkiv.schema` is the contract tag.
2. `D` = decode `C.data` (codec, chunks), parse as JSON. Check the projections it determines: `address`,
   `matchid`, `chainid`, `verifiedat`, `match`, `deployer` and `blocknumber` must equal what `D` gives (as the v3
   transform derives them).
3. For each lane with a code reference: fetch the `code` entity, check its `hash` attribute and the Keccak-256 of
   the decoded bytes against the contract's `creationcodehash`/`runtimecodehash`, and insert `"0x" + hex` at
   `/lane/onchainBytecode`. A code hash without a reference must describe a literal `onchainBytecode` in `D`.
4. Fetch the compilation `P` by `compilationref`. Check `P.hash = C.compilationhash`, decode `manifest`, check
   `SHA-256(manifest) = P.hash` and that the manifest is canonical JSON. Validate every reference as v3 did:
   JSON pointers, no duplicate or overlapping paths, local references only from `stdJsonInput`/`stdJsonOutput`
   to elsewhere (so no cycles), source indices and code slots that exist, depth below 64.
5. For each top-level field in v3's order (`compilation`, `additionalInput`, `sources`, `abi`, `signatures`,
   `metadata`, `storageLayout`, `transientStorageLayout`, `userdoc`, `devdoc`, `sourceIds`, `stdJsonInput`,
   `stdJsonOutput`) that the compilation has, and then for each lane member (`recompiledBytecode`, `sourceMap`,
   `linkReferences`, `immutableReferences`, `cborAuxdata`) of each lane: expand it exactly as v3's `expand_at`
   does (stored value, then non-local references, then local ones, each in manifest order) and insert it into
   `D`. Groups load on first use and are checked against their digest; a source is checked by SHA-256 against
   both `manifest.sources[i]` and its entity's `hash`; a code by Keccak-256 against `manifest.codes` and its
   entity's `hash`; the hydrated `abi` by SHA-256 against `C.abihash`; the hydrated `compilation` against the
   contract's compiler projections (`name`, `compilerversion`, `language`, `evmversion`, `optimizer`,
   `optimizerruns`, `viair`, as the v3 transform derives them).
6. With a field selection, only the selected fields' groups and dependencies are read, and the result keeps the
   seven minimal fields plus the selection. An attribute the query did not select (still listed in
   `attributeSchema`) is never taken for an absence: the entity is fetched again with every attribute, and where
   that is not possible (a saved readback) the read fails.

Chunk lists are bounded before anything is fetched (at most 64 MiB plus the codec byte, a key per 120,000 bytes), every chunk and the
joined value are checked, and decoded values stop at 64 MiB. The writer refuses values over that bound and writes a
contract all or nothing, so a failed record leaves no entity and no nonce behind.

Because steps 2 to 5 are v3's own insertion order, the output equals v3 hydration *including key order*: the
SafeProxy example's output is byte-identical to `docs/data/hydrated-contract.json` (23,188 bytes, 2-space
pretty JSON). Unit tests compare v4 against v3 hydration, as serialized bytes, on the processor's tricky
fixtures (escaped pointer keys `~` and `/`, sources referenced from arrays, null ABI, non-canonical hex spellings,
literal `$ref`/`$spill` keys, arbitrary-precision numbers, values large enough to chunk) and on 100,000 generated
records built to collide sources, code, ABI and other fields, all through one shared writer. `udc-check` does the
same on real contracts of a v3 bundle ([evidence](#prototype-and-evidence)).

JSON stays inside bytes attributes. Turning JSON subtrees into typed attributes was rejected: `str` stops at
128 bytes and attributes at 32, the HTTP contract needs exact spellings (string `"607"` vs number, null vs
absent, number lexemes), and typed values come back re-encoded (`u64` as hex quantities, addresses in
lowercase). Typed attributes are projections for queries; the JSON is the record.

### Dependency closure and reads

| Request | Entities and attributes | Queries |
| --- | --- | --- |
| Minimal (no `fields`) | Contract `data` | 1 |
| `fields=abi,compilation` | Contract; compilation `manifest`, `abi`, `compilation` | 2 |
| `fields=all` | Contract; compilation (all); its codes; sources; chunks | 3 rounds without chunked values (up to 6 with them), each one query per 8 keys |

Reads by key batch at most **8 keys per query** (`$key = key(a) OR $key = key(b) …`). Eight `OR` groups is our
node's planned-path bound; beyond it the node scans at most 4,096 entities and gives up, which on a 15-million
entity chain means a failed read. Selecting named attributes (`select.attributes: {abi: true, …}`) keeps the
hot read small; the node still reports the unselected names in `attributeSchema`, so a reader can tell
"not selected" from "absent" (`udc-hydrate` does).

`Reader` (`src/udc.rs`) fetches in rounds, so a read costs one query per round and per 8 keys rather than one per
entity:

1. the contract's own chunks (if `data` is chunked), its compilation and its on-chain code, by key. A read of
   `abi` and `compilation` alone selects only the compilation's `arkiv.schema`, `hash`, `manifest`, `abi` and
   `compilation`; any other read selects every attribute;
2. once the manifest is known, what the selected fields' references need, closed over local references: the chunks
   of the groups (and of `sourcerefs`) it decodes, the sources and the recompiled code;
3. the chunks of those sources and codes.

A key a round missed is fetched on its own, and an attribute a narrow selection left out is fetched again with
every attribute; neither happens on the corpus (no reference points into `abi` or `compilation`). A transport
(`read-arkiv`, the server, the UI) only answers "these keys, this selection" with batches of 8.

Measured on our node: for SafeProxy `fields=all` is 3 queries for 6 entities and `fields=abi,compilation` 2 queries
for 2 entities (`read-arkiv`, the server and `docs/udc-examples/safeproxy-node/reads*.json` agree); the 16 contracts
the sync wrote take 3 to 11 queries (the largest, 73 entities, reads 11). In detail, for SafeProxy:

- `fields=all`: 3 queries. (1) The contract by owner, schema and address, limit 2. (2) The compilation and the two
  on-chain codes by key. (3) The source and the recompiled creation code by key (the runtime code is shared with
  the on-chain one). Six entities.
- `fields=abi,compilation`: 2 queries, the second selecting only the compilation's `manifest`, `abi` and
  `compilation` (with `arkiv.schema` and `hash`).

### Consistency on each node

- **Our node:** pin one block. Every query of a read passes the same `atBlock`, the node serves it from its
  archive, and the reader checks the block's hash again at the end.
- **Jalebi:** only the head is readable, so a read cannot pin a block. It reads at the head and relies on two
  properties instead: only contracts are ever changed (patched in place), and a contract comes from one query;
  sources, codes, compilations and chunks are permanent and never patched or deleted, and every dependency is
  checked by content hash. A contract read at any moment is therefore one whole version whose dependencies all
  exist. A read that meets a failed check fails closed and can be retried.

## Identity, keys and deduplication

- **Keys.** Both nodes derive `keccak256(u256 chainId ‖ 0x4400000000000000000000000000000000000044 ‖ owner ‖
  u64 entity nonce ‖ u128 salt)` (our node's `derive_entity_key`, Jalebi's `derive_entity_address`, the SDK's
  `predictEntityKey`). Keys are not content-addressed: they depend on the owner's entity nonce. All six keys of
  the SafeProxy round trip were predicted before sending and matched what our node assigned.
- **Salt 0.** The writer uses salt 0 (`NO_SALT`). A prefill's keys are then a pure function of its creation
  order, so a bundle is reproducible and a converter can re-key it for another chain or owner mechanically
  (every `key` attribute, `sourcerefs` and chunk list). Predictable keys let others create entities that
  *reference* ours; readers always scope by `$owner`, so that is harmless.
- **Writing references.** Dependencies are created before dependents (sources, codes, chunks, compilation,
  contract), so a contract is visible only once everything it needs exists. In a prefill every key is known
  offline. The live writer (the UDC sync) writes in four levels, each mined and read back before the next is
  sent: chunks; sources and codes; compilations; contracts. Within a level no operation names another, so its
  transactions are independent; the keys come from the receipts (`EntityCreated`, salt 0), and the next level's
  references are rewritten from bundle keys to them. A reverted transaction stops the batch before anything names
  what it would have created; predicting keys across transactions in flight (`predictEntityKeys`) would let one
  reverted transaction shift every later key, so the writer does not.
- **Deduplication.** By content hash, as in v3: sources by SHA-256, code by Keccak-256, compilations by the
  manifest hash. The prefill writer keeps a hash-to-key map; a live writer looks up
  `$owner = addr(O) AND arkiv.schema = str('sourcify.v4.source') AND hash = bytes32(H)` and reuses the key. The
  indexed `hash` is what makes that lookup possible.
- **Binding.** A contract names its compilation twice: by key (`compilationref`, to fetch it) and by content
  (`compilationhash`, checked on read), so a contract pointed at another compilation fails, as v3's
  hash-carrying references did.
- **Contracts.** One per address, **patched in place** when Sourcify verifies the address again: a new match (a
  new `matchId`, e.g. partial to exact or another compilation) or a correction under the same `matchId`. The patch
  sets every attribute of the new version (with its indexed flag) and unsets (tombstones) those the new version
  lacks; the entity's key, owner and expiry stay, and nothing else is touched. A new compilation, code or source the
  new version needs is created first, so the patched contract never names a missing entity; the previous version's
  dependencies stay (they are shared and permanent), and so do the chunks of a replaced `data` value, so a reader
  holding the previous version still finds everything it names. The writer never moves a contract backwards: a
  match older than the chain's `matchid` is skipped. Because a patched contract keeps its creation position on both
  nodes, creation order is no longer `matchid` order, and paging uses `matchid` windows instead
  ([paging](#paging)).

## Lifetime, rent and ownership

- **Permanent, every kind** (`expiresAt = 2^64 − 1`). A dataset is an archive; dependencies must outlive
  contracts, and permanence makes that trivially true. Under the one-year rent cap a permanent entity costs
  exactly one year of rent on our node, so expiring entities would only add renewal transactions for 15 million
  entities. Rejected: finite lifetimes with periodic extension.
- **Owner: one key per chain** (decided). On each chain one dataset key creates and owns everything; our node's
  and Jalebi's datasets have different owners. Only the owner can make an entity permanent or extend it beyond one
  rent cap (`PermanenceOwnerOnly`) and only the owner can patch, so every reader filters by its chain's `$owner`
  (each dataset profile names it) and the chain's sync must sign with that key. A key per chain keeps a leaked key
  to one chain (the Jalebi key signs a 15-million-entity live load on a public testnet; our node's dataset is a
  genesis prefill, whose rows need no signature), keeps funding apart, and costs nothing: keys differ per chain
  anyway (the chain ID is in the derivation) and a sync target already names its own `ENTITY_OWNER` and writer key.
- **Rent on our node.** Storage units × 20 gwei per day, capped at one year: **7.3 × 10⁻⁶ GLM per unit**. The
  SafeProxy entities measured 19,403 units and paid 0.1416419 GLM (`rentFee`), exactly 19,403 × 7.3 × 10¹² wei. A
  genesis prefill of permanent rows is sponsored: no rent is charged.
- **Rent on Jalebi.** Not final: the GolemDB tokenomics draft prices storage per unit per block up front with a
  six-month maximum lifetime, and the price of a permanent entity is not specified. See
  [open questions](#open-questions).

## Query patterns on both nodes

Every query starts with the dataset scope

```text
$owner = addr(OWNER) AND arkiv.schema = str('sourcify.v4.contract') AND chainid = u64(1)
```

and is written in the subset both nodes accept: `str('…')` with `''` for a quote, typed hex literals, bare
`true`/`false`, no `NOT` or `!=`, no `BETWEEN`, ranges only on numbers, at most eight `OR` groups, `limit` at most
100. Counts use `arkiv_getEntityCount({query})`.

| Question (Search filter or Compare question) | Clauses after the scope |
| --- | --- |
| Contract at an address (`q` = address, `lookup`) | `address = addr(0x…)` (limit 2) |
| Name prefix (`q`, `name-prefix`) | `name STARTSWITH str('Flok')` |
| Same name (`name`, `same-name`) | `name = str('…')` |
| Compiler release / exact build (`compiler`, `same-compiler`) | `compilerversion STARTSWITH str('0.8.20+')` / `compilerversion = str('…')` |
| Language, EVM version, match quality | `language = str('Vyper')`, `evmversion = str('paris')`, `match = str('exact_match')` |
| Optimizer, viaIR (`optimizer`, `viair`) | `optimizer = true` / `optimizer = false`, `viair = true` |
| Optimizer runs (`runs`, new) | `optimizerruns = i32(200)` |
| Deployer (`deployer`, `same-deployer`) | `deployer = addr(0x…)` |
| Verified between dates (`from`, `to`, `recent`) | `verifiedat >= u64(T1) AND verifiedat <= u64(T2)` |
| Deployment block range (`bfrom`, `bto`) | `blocknumber >= u64(B1) AND blocknumber <= u64(B2)` |
| Match ID (`mid`) | `matchid = u64(N)` |
| Same ABI, runtime, creation code (`sameabi`, `sameruntime`, `samecreation`) | `abihash = bytes32(0x…)`, `runtimecodehash = bytes32(0x…)`, `creationcodehash = bytes32(0x…)` |
| Same compilation (`samecomp`) | `compilationhash = bytes32(0x…)` |
| Vyper reentrancy releases (`vyper-bug`) | `language = str('Vyper') AND (compilerversion STARTSWITH str('0.2.15') OR compilerversion STARTSWITH str('0.2.16') OR compilerversion STARTSWITH str('0.3.0'))` (3 groups of 5 literals) |

Every Search filter and every Compare question is a conjunction of positive clauses, so none needs negation.
`optimizer = false` is a positive clause on an indexed `bool`.

### Paging

Neither node sorts. Our node returns matches in creation order (record ID), Jalebi in block order and, within a
block, by transaction and key. A contract patched in place keeps its creation position on both (measured, table
above), so once a re-verification has patched a contract, node order is not `matchid` order on either node: the
key-set rule this proposal first had (continue from the largest `matchid` of the complete blocks seen) would skip
every match between a patched contract's old position and its new `matchid`. Cursors do not help either: our
node's needs a pinned block, Jalebi's dies with the next block.

The rule both nodes run relies on one property only, measured on both, whatever their order:

> a **window** query `… AND matchid >= u64(A) AND matchid <= u64(B)` (inclusive bounds) that returns **no
> cursor** returned every match in that window.

A page of `P` contracts after a cursor `C` (`P` below `limit`, which is at most 100), ascending:

1. Query the window `[C + 1, C + W]` (W: the previous page's width hint, or 65,536 at first). A window that
   reaches past 2^40 is open there (`matchid >= u64(C + 1)` alone): the mirror keeps Sourcify's match IDs below
   10^12, so an open window ends the walk in one query wherever the last match is.
2. **Complete** (no cursor): sort its rows by `matchid` and take what the page still needs. If the page fills, its
   last `matchid` is the next cursor and twice the page's span is the next width hint. If it is short, continue
   with the window after it: back to the rest of the last window that came back full, if any (a binary search),
   else four times wider (sixteen after an empty window).
3. **Not complete** (a cursor): narrow the window towards its near end and ask again, to whichever is nearer of
   the `need`-th smallest `matchid` among the rows returned (a subset's k-th smallest is never below the whole
   set's, so the narrowed window still holds the `need` first matches) and the window's midpoint. The midpoint
   matters when the rows come from the far end, as a descending walk's do on a prefilled chain (creation order is
   ascending there), and when a node returns a cursor with fewer rows than asked. When the narrowed part comes back
   empty, the rest of the full window is halved at once without asking for all of it first.

Descending pages (newest first) mirror it: windows `[C − W, C − 1]`, narrowed towards their upper end. Any further
positive clauses (a Search filter, a Compare question) are added to every window **in parentheses**, so an `OR`
cannot escape the scope, and every returned row's owner and `arkiv.schema` are checked. `matchid`s are unique per
dataset (`verify` checks it): two at a page boundary fail the walk rather than lose one. The reference
implementation is `src/udc_page.rs` (`ascending`, `descending`), tested on simulated node orders (creation order
with patched rows, block-and-key order, shuffled, trimmed pages) and 3,000 random walks; `udc-page` runs it over
RPC with one pinned block per walk.

Why it is exact on both nodes: completeness is the only thing it reads from a response, and neither node returns a
cursor when no rows remain (measured on both; our node also returns none when exactly `limit` rows match). A
cursor with rows to spare, or with fewer rows than asked, only narrows the window. Why it should be cheap on our
node (from its query planner, `arkiv-state-db-experiment` `docs/snapshot-query-plan.md`; not yet measured on a
prefilled chain, see [open questions](#open-questions)): range literals on one attribute form one run of the term
map over the window's values, and the planner drives a group by its smallest source, so a window of a few hundred
`matchid`s is read through its own run, not through the 7.9-million-entry `arkiv.schema` posting. An unbounded
`matchid > X` in the middle of a prefilled chain falls back to scanning that posting (the v3 sync's start-cursor
search ran into this), which is why the walk asks one only past 2^40, where few or no contracts are. With a
selective filter (Vyper, a deployer) the filter's posting drives the window instead.

Cost, in the tests on 60,000 dense contracts in creation order (pages of 20, limit 100): an ascending first page 2
queries, a descending first page from the very top about 40 (a binary search down from 2^40), every later page 1 in
both directions. Measured on our node over the sync's 16 sparse test contracts after the re-verification patch
(`udc/measure/results/our-node-window-paging-20261028.json`, every walk pinned to one block): node order puts the
patched contract (`matchid` 60,000,001) where it was created, between 21,561 and 5,888,028; every walk returns
`matchid` order, ascending and descending, with and without a `match` filter; four descending pages of 5 took 7, 1,
1 and 1 queries.

On our node a walk pins one `atBlock` for all its windows and checks that block's hash at the end: a snapshot. On
Jalebi each window is read at the head: a contract patched between two windows moves to its new `matchid`, so an
ascending walk can show it twice (once per version; a reader keeps the later one by key) and a descending walk can
miss it until the next walk. Page jumps become `matchid` jumps (or count by `arkiv_getEntityCount` on a window and
bisect); counts are not paged.

**Jalebi's anonymous budget.** At 10 cost units per call and 1,000 per window, an anonymous client gets about
100 calls per window, shared by everything behind one IP; a contract read is 1 to 3 queries plus dependencies.
The UI server and the HTTP server need an API key (`LIVE_ARKIV_ACCESS_KEY` in the UI, an `X-API-KEY` header in
the server).

- **Entity overhead:** 1,460 units each, 22.1 G units in all (26%).
- **Indexes:** 128 units per indexed attribute. A typical contract has 19 indexed attributes, 2,432 of its

- **Content:** compilations 13.43 GB (`artifacts` 11.77 GB, `manifest` 0.79 GB, `abi` 0.57 GB, `compilation`
  0.18 GB, `sourcerefs` 0.17 GB), code 13.91 GB, sources 3.42 GB, contract `data` 3.75 GB (474 bytes on average,
  against 995 bytes of v3 contract payload, which repeated the compilation hash in 22 references).

node at today's price would burn about **610,000 GLM** of rent, plus gas (851,282 gas for a 120,000-byte create,
measured; the SafeProxy batch of six used 305,658 gas at 1 gwei). Throughput bounds a live load too, at 2-second
blocks: 786,432 input bytes per block is about 34 GB a day (the 34.6 GB of values need at least a day), 1.5 million
new storage units per block need at least 55,469 blocks (31 hours), and 128 operations per block need at least
118,219 blocks for 15.1 million creates: **at least 66 hours of full blocks**. Jalebi would need its own figures
once its pricing is set.

## Migration

### Processor (this repository)

Implemented on this branch (steps 3 and 5); the v3 writer, readers and sync stay unchanged next to them for the
November milestone and can be removed after the cutover.

- **`process --format udc [--schema-prefix sourcify.v4]`** writes a v4 bundle with the same input, completion
  marker, worker and fail-closed rules as v3: `seed.json` version 2 (`sourcify-arkiv.udc-bundle.v1`: chain ID,
  owner, schema prefix, `firstNonce` 0, parts), `report.json` (`sourcify-udc-import.v1`: records, entities by kind,
  distinct sources, codes and compilations, bytes, storage units, parts with digest, size, entity count and first
  nonce), `SHA256SUMS` (parts, `report.json`, `seed.json`; `seed.json` is published last) and
  `entities/NNNNNN.jsonl`. Each line is one entity in creation order:
  `{"nonce":N,"key":"0x…","expiresAt":"0xffffffffffffffff","attributes":[{"name","type","indexed","value"}…]}`,
  attributes in name order in the node's RPC encoding except `bytes`, which is base64; the key is the salt-0 key of
  the bundle's chain, owner and nonce. A second record for an address is refused (one contract per address). There
  are no `payloads.bin` or `metadata.jsonl` audit files.
- **`verify`** reads `seed.json`'s version. A version-2 bundle needs `report.json` and `seed.json` in `SHA256SUMS`
  and is then checked line by line: nonces in order from `firstNonce`, every key the salt-0 key of its nonce,
  every entity permanent, within the node's rules (32 attributes, 128-byte `str`, unindexed `bytes`, ascending
  names) and the 120,000-byte budget, and within the format's schema (`udc::ATTRIBUTES`: each kind's attributes
  with type, indexed flag and whether required); every bytes value non-empty with a known codec, `sourcerefs`
  inline; every key it names (key attributes, `sourcerefs`, chunk lists) an earlier line of the right kind, and a
  contract's compilation and codes carrying the hashes it names (`compilationhash`, `creationcodehash`,
  `runtimecodehash`); chunk lists as long as their chunks; `firstNonce` 0; one contract per address and per
  `matchid`, one entity per content hash and kind; counts, distinct counts, bytes and storage units as
  `report.json` gives them. Values are not decompressed; `hydrate` checks content.
- **`pack`** verifies first (either version) and records `seedVersion` and `bundleFormat` in the archive record;
  **`upload`** stores the format as `x-amz-meta-bundle-format`, refuses an existing object whose format metadata
  differs, and `--expect-format udc|v3` refuses an archive of the other format.
- **`hydrate`** rebuilds every contract of a version-2 bundle with `udc::Reader` and writes the same NDJSON as v3
  hydration of the same records, byte for byte.
- **`read-arkiv --format udc`** reads one contract over RPC (`src/udc_rpc.rs`): pinned to one `atBlock` on our
  node (`--block`, else the head when it starts, hash checked at the end), at the head on Jalebi, `auto` by asking
  for a block 64 behind the head; key batches of 8; `--fields` (checked against the record's top-level fields)
  maps to attribute selection; 8 MiB per response by default; ServerBusy asked again 6 times, 100 ms doubling
  (never Jalebi's cost limit). `udc-page` pages contracts by the [window rule](#paging), one pinned block per walk
  (`--block`).
- **`arkiv/sync.ts` with `SYNC_FORMAT=udc`** (`arkiv/udc.ts`, UDC SDK `0.9.0-next.2`, installed as
  `@arkiv-network/sdk-udc` beside the v3 sync's `0.8.1-dev.1`): the batch's records become a v4 bundle; sources,
  codes and compilations already on the chain (`$owner`, `arkiv.schema`, `hash`) are reused, and their chunks not
  written again, when they are permanent, the owner's and hold the bundle line's content (another one is not
  reused: a fresh one is written); contracts are looked up by address and created, counted as synced (same
  content), patched in place (a `matchid` at least the chain's) or skipped (an older one, or two or more contracts
  for the address); only what a created or patched contract reaches is written, so a skipped contract leaves no
  dependencies behind; new entities go in the four levels above with references rewritten to the receipts' keys;
  every created or patched entity is read back by key (asked again for a node that lags its receipts) and
  compared attribute by attribute (name, type, indexed flag, value, owner, creator, expiry). Lookups tolerate a
  cursor (two rows are enough to tell "several"), and the start-cursor search works on a populated chain.
  Transactions hold at most `SYNC_MAX_TX_BYTES` (120,000) bytes of calldata and `SYNC_MAX_TX_OPS` (16, our node's
  limit) operations; an entity always fits one. Gas is estimated per transaction by default. This is the update path issue #13 asks for, for v4.
- **`crates/server --format udc`** (`backends/udc.rs`): the contract by address, then `udc::Reader` with key batches
  of 8 run under the server's RPC gate, field selection mapped to attribute selection, pinned or head view as
  `read-arkiv` (the `auto` probe 64 blocks behind the head), ServerBusy asked again with the same policy (never
  the cost limit), the request deadline checked before every fetch, decode and reference, default concurrency 4,
  the API key never printed. The HTTP contract, projection, signature and proxy policies do not change: every
  response equals the v3 path's for the same record ([evidence](#prototype-and-evidence)).
- **The pipeline and the daily seed** (`SEED_FORMAT=udc`, v3 the default): `pipeline/run.sh` and the Compose
  services run `process --format udc --schema-prefix SCHEMA_PREFIX`, the same `verify` and `pack`, and an upload
  that requires a v4 archive (`--expect-format udc`; a v3 upload refuses a v4 archive); `timings.json` records the
  format and prefix, so a bundle is never reused as the other format or under another prefix.
  `SEED_FORMAT=udc pipeline/daily.sh` (`deploy/sourcify-daily-seed-udc.service` and `.timer`, 04:00 UTC,
  `TimeoutStartSec=12h`) publishes `seed-inputs/udc/sourcify-ethereum-YYYYMMDD.tar.zst` and its own
  `seed-inputs/udc/sourcify-ethereum-latest.json` (with `seedFormat`, `bundleFormat`, `seedVersion`,
  `schemaPrefix`, `owner`, `arkivChainId`) from its own `data/runs-udc`. It refuses a prefix overlapping the v3
  `R2_KEY_PREFIX`, a `RUNS_DIR` of the v3 seed and a bundle that is not v4, so it never writes, replaces or
  deletes a v3 seed or the v3 `latest.json` that production reads. Like v3, it pauses the mirror's sync for
  `prepare` only ([decision 10](#decisions-of-2026-10-28)): `prepare` is bounded by `DAILY_PREPARE_TIMEOUT`
  (3600 s; its container is stopped before the sync starts again), both jobs take one lock for the pause, so neither restarts the sync during the other's `prepare`, and a
  marker kept while the sync is stopped lets the next run start a sync an earlier one could not. The v4 unit is
  ordered after the v3 one (a v4 start that comes with or during a v3 run waits for it), and both must run from
  one checkout (the lock is in its `data/`).
  `tests/daily.test.ts` checks the order of the calls against a stub `docker` (stop, prepare, start, then process
  with the lock free; the start also after a failed, timed-out or signalled prepare), a same-day resume without a
  second pause, the recovery of a sync left stopped, and the keys, pointer and deletions of both formats;
  `tests/pipeline.test.ts` runs `SEED_FORMAT=udc` on the fixture (the v4 hydration equals v3's). The units are
  repository files: nothing is installed or run by this change.
- Docs: `README.md`, `docs/server.md` and `docs/arkiv-reader.md` describe the v4 path. The docs site pages
  (`docs/*.html`) and `docs/data/` describe the v3 dataset that production serves and change with the cutover
  (step 11).

### Prefill converter (arkiv-state-db-experiment `scripts/sourcify-prefill.py`, arkiv-prefill)

A v4 bundle maps one line to one genesis row (codec 3, `ARKPFL02 ‖ u32(3) ‖ u64(rows)`), with no payload to
reinterpret:

- creator = owner; creation nonce = the line's nonce (0 to N−1, the bundle order); salt 0; expiry
  `u64::MAX` (a permanent-prefill launch, versions 3/4, rent sponsored); flags 0;
- attributes as cells: kind `01` indexed, `02` stored; engine tags (`bool` 01, `str` 02, `bytes` 03, `addr` 04,
  `bytes32` 0b, `u64` 0d, `i32` 10, `key` 40), names strictly ascending;
- checks: the node's row rules (32 attributes, 128-byte `str`, 128 KiB of `bytes`), the 120,000-byte budget, every
  key (attribute, `sourcerefs`, chunk list) naming an earlier row, digests and content hashes;
- re-keying for another chain or owner recomputes every key from (chain, owner, nonce, 0).

The bulk builder assigns record IDs in row order, so on a fresh chain creation order starts as `matchid` order; the
paging rule does not rely on it (patched contracts keep their position). This is a document-only change before 10 November; the converter code changes after
(arkiv-prefill's `main` and the node repository are not touched by this proposal).

## sourcify-mirror-node

[sourcify-mirror-node](https://github.com/Arkiv-Network/sourcify-mirror-node) is the PostgreSQL mirror of
sourcify.dev for Ethereum mainnet that the processor's `prepare` and its sync read. Checked on its `main`
(`4fb46cc`) without touching the live host or its database:

- **It does not know the Arkiv entity format.** Its code is the Sourcify schema, the published Sourcify server,
  `sync/sync.py` (follows sourcify.dev's `GET /v2/contracts/1?sort=asc&afterMatchId=…`, insert-only) and
  `import/import.ts`. The only Arkiv references are the `export/role.sql` comment and the nginx `/sync/` location.
- **Source fields: no change.** v4 stores the same record, built by `source/records.ts` from the eleven tables
  `export/role.sql` grants (`code`, `sources`, `signatures`, `compiled_contracts`, `compiled_contracts_sources`,
  `compiled_contracts_metadata`, `compiled_contracts_signatures`, `contracts`, `contract_deployments`,
  `verified_contracts`, `sourcify_matches`). The new contract attribute `optimizerruns` comes from
  `compilerSettings`, already read. No grant changes.
- **Sync behaviour v4 relies on, unchanged:**
  - `sourcify_matches.id` is sourcify.dev's `matchId`, inserted in list order, and `created_at` is `verifiedAt`.
    The Arkiv sync writes contracts in `matchId` order and a re-verification arrives as a newer `matchId`, which
    the sync patches in place; the paging rule needs neither order (it pages by `matchid` windows).
  - Matches from 10^12 on are the node's own and stay excluded (the paging rule's windows open past 2^40).
  - A seed is the database at one `matchId`: the daily run stops the mirror's sync during `prepare` only (about
    5 minutes), for v3 and v4 alike; v4's process (about 6 hours) runs with the sync running.
- **Known edges, not new with v4:**
  - The import's `skipped-matches.json` back-fill inserts older `matchId`s once, at setup. Done before an Arkiv
    sync starts, it is harmless; inserted behind a running Arkiv cursor, those matches are never synced (true for
    v3 too).
  - Upgrades under the same `matchId` reach the mirror only with the next export ("Known issues"). v4 handles a
    changed record for an existing `matchId` as a patch of the contract entity, which keeps its creation position.
- **`/sync/` dashboard and nginx: no change.** The page is written by the processor's `arkiv-sync-dashboard` from
  `targets/*.env`; a UDC sync target is one more target on the same page, and the nginx locations serve static
  files whatever the target. The dashboard reads chains with `eth_*` calls only (blocks, gas price, balances,
  nonces), which both nodes serve; on Jalebi its `getBlock` of an earlier height reads block data, not state.
- **Docs: no change needed.** The README describes the dashboard as the processor's syncs to Arkiv chains, which
  stays true.

So the mirror needs no code, configuration or documentation change, and no `udc` branch was created there. It
appears in the plan only as a read-only source.

### Independent review of the prototype

An independent review of the prototype (a separate agent, with a differential fuzzer against v3 hydration) found
four cases where v4 differed from v3 and gaps in the checks; all are fixed on this branch, with regression tests:

- contract-local values that v3 restores from references were re-sorted (now stored in v3's order);
- the `abihash` check compared the stored, stripped ABI (now the hydrated ABI);
- a recompiled bytecode spelled like a source text had no code slot (now any referenced code takes a free slot);
- an on-chain code reference followed by another reference in its lane changed key order (now stays literal);
- an unselected code reference read as absent (now an error), a contract could be pointed at another compilation
  (now `compilationhash`), chunk lists were not bounded before fetching (now they are), the writer was not all or
  nothing and could write values the reader refuses (now it is and cannot), and hydration copied a parent value per
  reference (now linear).

They were latent for the 2026-10-23 corpus: it has no contract-local reference outside the two on-chain code
paths, every compilation code reference names a lane's recompiled bytecode (the full-corpus size scan assumes it),
and none of its 878,392 compilations has a reference into `abi` or `compilation`.

### Independent review of steps 3 and 5

Three independent reviewers (separate agents with the diff and this document, not the implementer's conclusions)
read the change, ran the suites and built their own harnesses: a batched-reader harness (1,710 records × 21
selections, batched = one by one = v3), 2,065 tampering mutations × 7 selections (none passed silently), paging
oracles (40,000 and 200,000 random walks, adversarial orders and boundaries; none inexact), adversarial bundles,
fake chains and read-only checks on our node. What they found, and what changed:

| Finding | Severity | Fix |
| --- | --- | --- |
| The sync's start-cursor probe refused a cursor, so a sync without `--start-after` could not start (or restart) on a chain with more than two contracts above its probe | High | Lookups and the probe tolerate a cursor; tested on a fake chain, and live: a dry run finds the chain's highest `matchid` |
| Descending pages crept: a full window only moved its far end to the rows returned, which on a prefill are the smallest; about 98,750 queries per page on 7.9 million contracts in simulation | High | A full window narrows to the nearer of that row and the midpoint, a short window returns to the rest of the last full one, an empty half halves the rest at once, and the width hint comes from the page's rows: a descending first page about 40 queries, later pages 1 |
| A chunked `sourcerefs` (a compilation of over 3,749 sources) hid its source keys in chunk data under a digest: `verify` passed it, the sync would write stale keys, re-keying would break | Medium | Never chunked; the writer refuses such a compilation, and `references`, the readers, `verify` and the sync refuse any codec but `00` |
| Reused dependencies were not checked, so a rerun after a failed read-back reused whatever had the hash | Medium | A dependency is reused only when permanent, the owner's and of the bundle line's content |
| `read-arkiv --format udc` capped responses at 1 MiB; a batch of 8 chunks is about 2 MB | Medium | 8 MiB by default for udc |
| The `auto` view probed one block behind the head | Medium (suspected) | 64 blocks behind |
| Completeness was "fewer than `limit` rows or no cursor": a node trimming a page with a cursor would lose rows | Low–medium (suspected) | Complete means no cursor; a trimmed page narrows by bisection |

### Values

Select `attributeSchema: true` with `attributes` to get each attribute's type and indexed flag; an attribute
listed there but not returned was not selected, never absent. Values arrive in the node's RPC encoding by type:
`bool` a JSON boolean, `i32` a JSON number, `u64` a `0x` quantity (`matchid` is the record's `matchId`,
`verifiedat` its `verifiedAt` in Unix seconds), `str` a string (indexed strings are projections: control
characters become U+FFFD, more than 128 bytes a 125-byte prefix and `…`), `addr` 20 bytes, `bytes32` and `key`
32 bytes and `bytes` any length, all as lowercase `0x` hex. The attributes of each kind are in
[Attributes per kind](#attributes-per-kind); `udc::ATTRIBUTES` in `src/udc.rs` is the same table in code.

A `bytes` value (every one except a chunk's `data`) is a codec byte and a body:

| Codec | Body | Decoding |
| --- | --- | --- |
| `00` | the value | as is |
| `01` | raw DEFLATE (RFC 1951) | `new DecompressionStream("deflate-raw")`, Node `zlib.inflateRawSync` |
| `02` | `sha256(joined)` (32 bytes) ‖ big-endian `u32` length ‖ 32-byte chunk keys | refuse a length over 64 MiB or a key count other than ⌈length / 120,000⌉ before fetching; fetch the `chunk` entities, join their `data` (each at most 120,000 bytes), check length and SHA-256, then decode the joined bytes, which start with `00` or `01` again |

Decoded values stop at 64 MiB. Contract `data` and compilation `manifest`, `abi`, `compilation` and `artifacts` are
UTF-8 JSON (parse numbers losslessly); source `content` is the UTF-8 text; code `code` is the raw bytecode (`0x` +
lowercase hex where the record has it); `sourcerefs` is codec `00` and the 32-byte source keys in
`manifest.sources` order.

### Reading one contract

1. The contract: scope `AND address = addr(0x…)`, `limit 0x2`, select `{key, owner, creator, expiresAt,
   attributeSchema, attributes: true}`. No row: not found; two: ambiguous (an error, never a choice).
2. Dependencies by key: `$key = key(K1) OR … OR $key = key(K8)`, at most 8 keys per query, `limit` the number of
   keys, the same select (or `attributes: {"arkiv.schema": true, …}`). In any order, every requested key must come
   back, with the dataset owner and the expected `arkiv.schema` kind. Fetch in the rounds of
   [Hydration](#dependency-closure-and-reads); for `fields=abi,compilation` select only the compilation's
   `arkiv.schema`, `hash`, `manifest`, `abi` and `compilation`.
3. Hydrate as `Reader::hydrate` does ([algorithm](#algorithm)), with every check: projections against `data`, code
   Keccak against `creationcodehash`/`runtimecodehash` and the code's `hash`, `compilationhash` = the
   compilation's `hash` = SHA-256 of its manifest bytes, a canonical manifest, group digests, source SHA-256
   against `manifest.sources` and the source's `hash`, the hydrated ABI's SHA-256 against `abihash`, chunk lists,
   `sourcerefs` inline (codec `00`), and the search projections against the record (`deployer`, `blocknumber`
   always; `name`, `compilerversion`, `language`, `evmversion`, `optimizer`, `optimizerruns`, `viair` when the
   `compilation` field is read). The result is the v3 record, key order included.
4. Views: on our node read the head's number once and send it as `atBlock` (hex) on every query of the read;
   every response's `blockNumber` must equal it; check the block's hash at the end. On Jalebi send no `atBlock`.
   To tell them apart at run time, ask for a block 64 behind the head: our node answers, Jalebi refuses with
   `-32006` ("not retained").
5. Our node answers HTTP 429 / `-32010 ServerBusy` when about 8 requests are in flight: keep at most 4 in flight and
   ask again after 100, 200, 400, 800 and 1,600 ms (6 attempts, within the request's deadline; `read-arkiv`, the
   server and the sync do the same). Jalebi's 429 `ANON_COST_LIMITED` is not busy (its window resets in minutes):
   fail at once. Its anonymous budget is about 100 calls per window per IP: the UI server needs an API key
   (`X-API-KEY`).
6. Response size: a key batch of 8 entities of up to 120,000 bytes is about 2 MB of hex; allow 8 MiB per response
   (the server's and `read-arkiv`'s default).

### Paging Search and Compare lists

The [window rule](#paging), exactly (inclusive bounds; a window is complete when its response has no cursor):

```ts
const TOP = 2n ** 40n, MAX = 2n ** 64n - 1n // windows are open beyond TOP (Sourcify match IDs stay below 10^12)
type Row = { matchid: bigint; key: string /* plus the summary attributes the list shows */ }
// query(lo, hi, limit): rows of `scope AND (filter) [AND matchid >= u64(lo)] [AND matchid <= u64(hi)]` in any
// order, every row checked for the dataset's owner and `<prefix>.contract`, and complete = !cursor. One pinned
// atBlock per walk on our node (its hash checked at the end), the head on Jalebi.
async function ascending(query, after: bigint | null, size: number, limit = 100, width = 65_536n) {
  if (size < 1 || size >= limit) throw new Error('a page must be smaller than the query limit')
  const rows: Row[] = []
  let start: bigint | null = after === null ? 0n : after === MAX ? null : after + 1n
  let fullFar: bigint | null | undefined // far end (null: open) of the last window that came back full
  let presumedFull = false
  while (start !== null) {
    const need = size - rows.length
    let lo: bigint | null = start > 0n ? start : null
    let hi: bigint | null = fullFar !== undefined ? fullFar : start + width - 1n < TOP ? start + width - 1n : null
    let skip = presumedFull && hi !== start
    presumedFull = false
    let found: Row[]
    for (;;) {
      let complete = false
      found = []
      if (!skip) {
        const r = await query(lo, hi, limit)
        if (r.rows.some(x => (lo !== null && x.matchid < lo) || (hi !== null && x.matchid > hi))) throw new Error('a row outside its window')
        ;({ rows: found, complete } = r)
      }
      skip = false
      found.sort((a, b) => (a.matchid < b.matchid ? -1 : a.matchid > b.matchid ? 1 : 0))
      if (complete) break
      fullFar = hi // not complete: narrow towards the near end
      const far = hi ?? MAX, mid = start + (far - start) / 2n
      const byRows = found[need - 1]?.matchid
      const bound = byRows !== undefined && byRows < mid ? byRows : mid
      if (bound === far) throw new Error('a window could not be narrowed (two contracts with one matchid?)')
      hi = bound
      width = bound - start + 1n
    }
    if (found.length >= need) {
      if (found[need]?.matchid === found[need - 1]!.matchid) throw new Error(`two contracts share matchid ${found[need - 1]!.matchid}`)
      rows.push(...found.slice(0, need))
      return { rows, next: rows.at(-1)!.matchid, width: (rows.at(-1)!.matchid - rows[0]!.matchid + 1n) * 2n }
    }
    rows.push(...found)
    start = hi === null || hi === MAX ? null : hi + 1n
    if (fullFar === hi) fullFar = undefined
    else if (fullFar !== undefined && found.length === 0) presumedFull = true
    if (fullFar === undefined) width *= found.length ? 4n : 16n
  }
  return { rows, next: null, width }
}
// descending(before): the mirror image. start = before - 1 (or MAX from the top); a window is
// [max(min(start, TOP) - width + 1, 0), start] (lower open at 0, upper open at MAX); rows are sorted descending;
// a full window raises its lower end to the nearer of the need-th largest row and the midpoint; the walk steps
// down below the lower end. src/udc_page.rs is the reference for both.
```

The page cursor is the last row's `matchid`; the next page starts after it (before it, descending). Pass the
returned `width` on as a hint. On Jalebi a walk reads the head, so an ascending walk may meet a contract twice after
a patch (keep one per key) and a descending walk may miss one patched meanwhile. Counts: `arkiv_getEntityCount`
with the same query (and `block` on our node). Page jumps: walk, or bisect a `matchid` bound with counts. Never
`NOT`, `!=` or `BETWEEN` (Jalebi refuses them); ranges only on numbers.

## Decisions of 2026-10-28

1. **Generation name:** `sourcify.v4.<kind>` (the proposal's default).
2. **Indexed set on the contract:** every indexed attribute stays as proposed, `chainid`, `isproxy`/`proxytype` and
   `evmversion` included ("for prefill and Sourcify price does not matter").
3. **Stored signatures:** kept in `artifacts`.
4. **A smaller hot read: no separate `digests` attribute** (decided here). The hot read must check `abi` and
   `compilation` against the compilation's identity, and the digests are bound to it only through the manifest
   (`hash` = SHA-256 of the manifest). A `digests` attribute would need a binding of its own: a second hash on the
   compilation, or an identity computed from parts, changing every reader and the converter. The manifest also says
   whether a hot field needs references restored; the corpus has none, but the format allows them (the tests build
   them), and without the manifest a reader could not tell. The saving, about 0.7 KB per hot read (1.75 KB to
   1.03 KB), is small against the read's two round trips. A later generation can add it.
5. **zstd:** none (the default); codec `03` stays free.
6. **Jalebi pricing and permanence:** open (below).
7. **Jalebi access:** open (below).
8. **Contract updates: patch in place** (the user's decision). A re-verification under a new `matchId` patches the
   contract entity; its key stays. Paging moves from the `matchid` key set (which assumed that creation order is
   `matchid` order) to [`matchid` windows](#paging), measured to hold on both nodes after patches; the sync patches
   ([migration](#processor-this-repository)); readers and this document follow.
9. **Owner key: one per chain** (decided here, [ownership](#lifetime-rent-and-ownership)).
10. **`process --format udc` speed: accepted** (the user's decision: "6 hours no problem, just make sure the mirror is
    down only for initial copy phase"). No parallel writer; the daily v4 seed runs about 7 hours. The mirror's sync
    is paused for `prepare` only: `pipeline/daily.sh` starts it again before process (also after a failed
    `prepare` or a signal), a same-day resume whose `prepare` completed does not pause it again, and v3 and v4
    jobs share one pause lock ([migration](#processor-this-repository)).

## Open questions

1. **Jalebi pricing and permanence.** What a permanent entity costs on Jalebi, who pays for a 15-million entity
   load, and whether Jalebi will accept entities in genesis.
2. **Jalebi access.** An API key for the dataset's readers and servers, and the transaction-size limit its pool
   actually runs with.
3. **Window cost on a prefilled chain.** The window rule's cost on our node is the planner's (a range run over the
   window), not yet measured on a chain holding 7.9 million contracts; measure it on the step-9 genesis, and on
   Jalebi once it holds a dataset.
4. **Throughput of `process --format udc`: accepted, no longer open** ([decision 10](#decisions-of-2026-10-28)).
   366 records/s on 100,000 records, bound by the single ordered writer (DEFLATE at level 9): about six hours for
   the full corpus, against v3's parallel gzip, with the mirror's sync paused for `prepare` only. Should it matter
   later, moving the v3-to-v4 layout into the transform workers and encoding only the distinct values in a pool
   (deterministic: encodings are pure, keys are assigned in order) would bring it near v3's speed.
5. **Orphaned chunks.** A patch that replaces a chunked contract `data` leaves the old chunks (permanent, rent paid
   once), so that a reader of the previous version still finds them; none of the corpus's contracts is chunked.
   Chunks have no hash to be found by, so a batch that fails after its chunk level and is retried writes its new
   chunks again (about 0.9 GLM per full chunk on our node); the earlier ones stay unreferenced.
6. **Re-verifications the mirror ranks lower.** `source/prepare.ts` keeps one match per address, the better match
   first and then the newer one. A newer re-verification of lower quality (exact to partial) is therefore never
   selected and never patched in; whether the dataset should follow the newest match instead is a product question
   (it is how v3 behaves too).

## Blockers

On **our node**, nothing blocks the plan: limits, permanence, rent, key prediction, codec 3 prefill and the
queries are in place and measured. Only cursor paging without `atBlock` is missing, which v4 does not need.

On **Jalebi**:

1. **No entities in genesis.** The dataset can only arrive by transactions: about 15.1 million creates, each
   under 128 KiB.
2. **No negation.** `NOT` is not implemented and `!=` is refused. The proposed queries need neither, but any
   future "not X" question cannot be asked.
3. **Head-only state.** No pinned reads; consistency rests on single-query contract reads, dependencies that are
   never changed, and content hashes.
4. **Cursor paging within one block only** (measured); v4 pages by `matchid` windows on both nodes.
5. **Anonymous budget.** 1,000 cost units (100 calls) per window per IP: readers need an API key.
6. **Pricing not final**, and the transaction-size limit is reth's default unless the deployment changed it
   (not measurable without a write).
